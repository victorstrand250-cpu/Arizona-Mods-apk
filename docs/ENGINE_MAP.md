# Карта libag-client.so

Разбор нового движка Arizona Mobile, `libag-client.so` из
`ARIZONA.ONLINE_v17.7.1.apk`, arm64-v8a. Библиотека собрана stripped: имён
своих функций в ней нет, только имена импортов и JNI-экспортов.

Все смещения — **от базы загруженной библиотеки**. Базу даёт
`memory.getclientbase()`.

## Найденное

### Игроки

| Смещение | Тип | Что это |
|---|---|---|
| `+0x150E950` | массив | слоты игроков, шаг **336** байт, указатель на объект в начале слота |
| `+0x1589F50` | `uint16` | номер своего слота; `0xFFFF` — слота нет |

Внутри объекта сущности. Пешеход и транспорт делят общую базу — движок
читает позицию по одним и тем же смещениям и у того, и у другого:

| Смещение | Тип | Что это |
|---|---|---|
| `+56` | `float[3]` | позиция x, y, z |
| `+260` | `float[3]` | скорость x, y, z |
| `+1112` | указатель | транспорт, в котором сидит игрок |
| `+1120` | `uint8` | флаг «внутри транспорта» |

Скорость в км/ч движок считает как `|скорость| * 175.0`.

### Сущности мира

Пулы сущностей движок держит в куче, а в библиотеке лежит только указатель
на массив. Мест в каждом пуле — предел, стоящий рядом в коде.

| Смещение | Мест | Что это |
|---|---|---|
| `+0x315AE18` | 2000 | указатель на массив сущностей |
| `+0x315AE28` | 1000 | указатель на массив сущностей |
| `+0x3159650` | 1000 | указатель на массив сущностей |

Сразу за массивом указателей лежит карта занятости — по байту на место:

```asm
699c14:  adrp x8, 0x3159000
699c18:  ldr  x21, [x8, #1616]     ; сам массив
699c1c:  mov  w8, #0x1f40          ; 8000 = 1000 мест * 8 байт
699c20:  ldr  x0, [x21, x19, lsl #3]
699c28:  strb wzr, [x21 + x19, x8] ; байт занятости
```

Вот место, где сущность берут из пула и сразу читают её позицию — оттуда и
все смещения полей:

```asm
56dba0:  adrp x8, 0x315a000
56dba8:  ldr  x8, [x8, #3608]      ; массив по указателю
56dbb0:  ldrh w9, [x22, #172]      ; номер места
56dbb4:  cmp  w9, #0x7cf           ; предел, 2000 мест
56dbbc:  ldr  x10, [x8, x9, lsl #3]
56dbc4:  ldr  d0, [x10, #56]       ; позиция x и y
56dbc8:  ldr  s1, [x10, #64]       ; позиция z
56dbe4:  ldr  s2, [x10, #268]      ; скорость z
```

Поля сущности — те же, что у игрока: пешеход, транспорт и предмет мира
происходят от одного класса.

| Смещение | Тип | Что это |
|---|---|---|
| `+56` | `float[3]` | позиция |
| `+108` | `int16` | номер модели (230 обращений в коде) |
| `+260` | `float[3]` | скорость |
| `+980` | `int32` | состояние; 49 — за рулём |
| `+1112` | указатель | транспорт |
| `+1120` | `uint8` | флаг «внутри транспорта» |

### Описания моделей

| Смещение | Тип | Что это |
|---|---|---|
| `+0x3110540` | массив | указатели на описания моделей, шаг 8, **30300** мест |

Внутри описания:

| Смещение | Тип | Что это |
|---|---|---|
| `+29` | `uint8` | тип модели |
| `+44` | `uint16` | номер модели |
| `+32` | указатель | геометрия с габаритами |

```asm
5251f8:  mov  w8, #0x765c          ; предел 30300
5251fc:  cmp  w20, w8
525204:  adrp x8, 0x3110000
525208:  add  x8, x8, #0x540
52520c:  ldr  x22, [x8, x20, lsl #3]
525214:  ldrb w8, [x22, #29]       ; тип
525224:  lsl  w8, w9, w8
525228:  mov  w9, #0x4e0           ; маска допустимых типов
52522c:  tst  w8, w9
```

Маска `0x4E0` пропускает типы 5, 6, 7, 8 и 10.

Этот массив поначалу был принят за пул сущностей — из-за чего ESP по
объектам ничего не рисовал. Отличается он однозначно: индекс сюда берут
прямо из сущности (`ldrsh w, [сущность, #108]`, 230 мест), сущность читают
по `+56`, а описание модели по `+56` не читают никогда.

### Радар

| Смещение | Тип | Что это |
|---|---|---|
| `+0x9AF7B8` | `uint8` | радар показан |
| `+0x117E384` | `uint8` | радар круглый (1) или прямоугольный (0) |
| `+0x9948B0` | `float` | радиус |
| `+0x9948B4` | `float` | X на экране |
| `+0x9948B8` | `float` | Y на экране |
| `+0x3923FF8` | указатель | объект радара |

Найдено через JNI-методы `SetupHudDisplay` и `drawGameRadarCircle`: сами они
только кладут задачу в очередь, а пишет глобалы уже обработчик очереди
(`0x74A6FC` и `0x74A79C`). Java эти методы не зовёт, но код отрисовки радара
эти же глобалы читает — значит, состояние настоящее.

### Камера

| Смещение | Тип | Что это |
|---|---|---|
| `+0x9C1A00` | указатель | `rw::engine` — корень графической части |

Движок рисует на **librw**: в библиотеке остались пути его исходников
(`/usr/src/vendor/librw/src/*.cpp`), а значит раскладка структур известна не
на глазок, а по заголовкам. Сам `rw::engine` опознан по функции
`defaultBeginUpdateCB`, которая в librw выглядит так:

```cpp
engine->currentCamera = cam;
Frame::syncDirty();
engine->device.beginUpdate(cam);
```

По `0x298018` лежит ровно она:

```asm
298024:  adrp x20, 0x974000
29802c:  ldr  x20, [x20, #2944]    ; GOT -> 0x9C1A00, это rw::engine
298030:  ldr  x8,  [x20]           ; сам Engine
298034:  str  x0,  [x8]            ; engine->currentCamera = cam
298038:  bl   0x29C300             ; Frame::syncDirty()
298040:  ldr  x1,  [x8, #152]      ; engine->device.beginUpdate
298050:  br   x1
```

Дорога от `rw::engine` до экранных координат:

| Шаг | Смещение | Что |
|---|---|---|
| `Engine::currentCamera` | `+0` | указатель на камеру |
| `Camera::object.object.parent` | `+8` | кадр камеры |
| `Camera::viewWindow` | `+56` | `x` = тангенс половины поля зрения |
| `Camera::viewMatrix` | `+88` | готовая матрица мир → экран |
| `Frame::ltm` | `+112` | положение камеры в мире |

Раскладка перепроверена по коду: по `0x29C2D0` движок пишет в `ltm` по
смещению 112, а `privateFlags` читает по смещению 3 — ровно как в
`rwobjects.h`.

Матрица вида отдаёт доли экрана от нуля до единицы сразу, поэтому ни поля
зрения, ни соотношения сторон, ни разворотов осей подбирать не нужно:

```
u = right.x*x + up.x*y + at.x*z + pos.x
v = right.y*x + up.y*y + at.y*z + pos.y
w = right.z*x + up.z*y + at.z*z + pos.z
экран = (u/w * ширина, v/w * высота)
```

### Время суток

| Смещение | Тип | Что это |
|---|---|---|
| `+0x113E020` | `uint8` | перещёлкнуть время немедленно |
| `+0x113E024` | `uint8` | час, 0..23 |
| `+0x113E028` | `uint8` | минута, 0..59 |
| `+0x113E02C` | `uint16` | секунда |
| `+0x113E030` | `int32` | миллисекунд на игровую минуту (по умолчанию 1000) |
| `+0x113E034` | `int32` | когда была прошлая минута |
| `+0x1318F30` | `uint32` | время движка в миллисекундах, 391 ссылка |
| `+0x35E4E9C` | `int32` | вспышка молнии, поднимает яркость сцены |

Найдено декомпиляцией. Функция, которая выбирает две точки суток и смешивает
их, начинается с чтения часов:

```c
fVar70 = (float)*0x113E028;                        // минуты
fVar90 = (float)*0x113E024;                        // часы
fVar90 = fVar70/60.0 + *0x113E02C/3600.0 + fVar90;
if (23.999 < fVar90) fVar90 = 23.999;
```

А ход часов — в тике мира:

```c
if (*0x113E030 < *0x1318F30 - *0x113E034) {
    *0x113E034 += *0x113E030;
    if (++*0x113E028 > 59) { *0x113E028 = 0;
                             if (++*0x113E024 > 23) *0x113E024 = 0; }
}
```

Погоды как отдельной величины в движке нет. Таймцикл здесь — восемь точек
суток без деления по погоде, что видно и по ключам `DATA/TIMECYC.JSON`:
`Ambient`, `Directional`, `SkyZenith`, `FogStart`, `DrawDistance`,
`PostFXRed/Green/Blue`, `WaterRGBA` и подобные, все на час. Слова `weather`
в библиотеке нет вовсе. Поэтому «сменить погоду» здесь — это сменить время
суток: освещение, небо, туман и дальность прорисовки движок берёт из
таймцикла по текущему часу.

### Отладочный редактор таймцикла

| `+0x35E5028` | `bool` | показывать окно `Timecycle editor` |

## Как это было найдено

### Экспортируемый метод как точка входа

Библиотека stripped, но JNI-методы экспортируются по именам — иначе ART не
смог бы их вызвать. Среди них нашёлся `GTASA.getLocalVehicleSpeed`: всего
100 байт, но ему приходится дойти до игрока и его транспорта.

```asm
745b10:  adrp x8, 0x1589000
745b1c:  ldrh w8, [x8, #3920]      ; индекс своего слота
745b14:  mov  w9, #336             ; шаг слота
745b20:  umull x8, w8, w9
745b24:  adrp x9, 0x150e000
745b28:  add  x9, x9, #0x950       ; массив игроков
745b2c:  ldr  x8, [x9, x8]         ; объект игрока
745b30:  cbz  x8, ret
745b34:  ldrb w9, [x8, #1120]      ; флаг «в транспорте»
745b38:  ldr  x8, [x8, #1112]      ; транспорт
745b48:  ldr  s0, [x8, #264]       ; скорость y
745b4c:  ldr  s1, [x8, #260]       ; скорость x
745b58:  ldr  s1, [x8, #268]       ; скорость z
745b68:  fsqrt s0, s0              ; длина вектора
745b5c:  mov  w8, #0x432f0000      ; 175.0
745b6c:  fmul s0, s0, s1           ; км/ч
```

Одна функция дала и массив, и индекс, и шаг, и три смещения полей.

### Позиция

Дальше по всем 407 местам, где код обращается к массиву игроков, собрана
частота смещений. Среди них нашлась вот такая последовательность —
это функция «дай координаты игрока»:

```asm
5495d4:  ldr  x9,  [x10, x9]     ; объект игрока из массива
5495dc:  ldr  x10, [x9, #1112]   ; транспорт
5495e0:  ldrb w11, [x9, #1120]   ; флаг «в транспорте»
5495ec:  csel x9,  x10, x9, ne   ; берём транспорт, иначе пешехода
5495f0:  ldr  d1,  [x9, #56]     ; x и y одной парой
5495f4:  ldr  s0,  [x9, #64]     ; z
```

`csel` здесь и доказывает, что у пешехода и транспорта общая база: движку
всё равно, чью позицию читать, смещение одно.

### Редактор таймцикла

Во всём движке у `ImGui::Begin` (`0x8dee00`) ровно три вызова, и два из них
внутренние окна самого ImGui (`Debug##Default`, `###NavWindowingList`).
Третий:

```asm
7a4acc:  adrp x9, 0x35e5000
7a4ad8:  ldrb w8, [x9, #40]      ; флаг +0x35E5028
7a4adc:  cbz  w8, пропустить
7a4ae8:  adrp x0, "Timecycle editor"
7a4af4:  add  x1, x1, #0x28      ; тот же адрес как p_open
7a4b04:  bl   ImGui::Begin
```

Кнопки `00:00`…`21:00` внутри пишут номер слота в `+0x35E5024`.

## Чего найти не удалось

### Матрица камеры

Нашлась — см. раздел «Камера» выше. Со стороны вызовов GL был тупик: движок
пишет их в командный буфер, и указатель на матрицы в аргументах — копия
внутри буфера. Дорога открылась с другой стороны: библиотека собрана поверх
librw, а у него есть `rw::engine`, от которого до камеры два разыменования.

Поиск камеры по форме данных (`memory.findmatrix` и кнопка «Найти камеру» в
`/recon`) остался как запасной путь на случай, если игра обновится и
смещение `rw::engine` уедет.

### Ник игрока

Не найден статически. Движок разбирает его из ответа сервера — строка
`nickname` встречается ровно в одном месте (`0x6D8040`), и это разбор JSON,
а не поле структуры. Зато на живой игре смещение находится за секунду:
`/recon` → «Слот» перебирает и слот игрока, и начало объекта сущности и
показывает всё, что похоже на текст.

## Как искались пулы

Массив игроков нашёлся через экспортируемый JNI-метод. Дальше стало понятно,
что искать: **глобальный массив, к которому обращаются по индексу**. Узоров
три, и все перебираются автоматически:

* `mov wN, #шаг` + `umull` + `ldr xR, [xБаза, xСмещение]` — массив структур
  фиксированного размера. Так нашёлся массив игроков (шаг 336).
* `ldr xR, [xБаза, xИндекс, lsl #3]`, где база пришла из `ADRP+ADD` —
  массив указателей прямо в `.bss`. Так нашёлся массив описаний моделей.
* то же, но база пришла из `ldr xБаза, [xN, #imm]` после `ADRP` — то есть
  глобал хранит **указатель на массив**, а сам массив в куче. Так нашлись
  три пула сущностей, которые первым узором не видны вовсе.

Мало найти массив — надо понять, что в нём. Здесь помогает отпечаток полей:
от места, где код берёт элемент, вперёд по инструкциям собираются все
обращения по смещениям. У сущности в лидерах `+56` (позиция) и `+108`
(модель), у описания модели — `+29` и `+44`, а `+56` не встречается ни разу.
Именно так выяснилось, что `0x3110540` — не пул сущностей: он выглядел
главным по числу обращений, но отпечаток у него чужой.

## Чем это искалось

Инструменты писались под задачу, все в `tools/`:

* **перекрёстные ссылки** — разбор пар `ADRP+ADD` и `ADRP+LDR` по всему
  `.text`: 47 тысяч ссылок на 16 тысяч целей. По ним находится, какой код
  трогает какую строку или глобал.
* **разбор PLT** — сопоставление заглушек с именами импортов через
  `.rela.plt`. В stripped-библиотеке имена импортов остаются, и через них
  можно зацепиться за код.
* **карта полей** — от места, где код берёт указатель игрока из массива,
  вперёд по инструкциям собираются все обращения по смещениям. Частота
  смещения говорит о важности поля, форма инструкции — о его размере.
* **пулы за указателем** — разбор мест, где глобал хранит указатель на
  массив, с пределом индекса и картой полей элемента. Этим найдены пулы
  сущностей мира.
* **кто трогает глобал** — по точному адресу выводится весь код, который его
  читает и пишет, с формой инструкции. Так подтверждаются находки: если
  глобал пишет только один обработчик, а читает код отрисовки, значит это
  настоящее состояние, а не мусор.
* **поиск по форме данных** — уже в самой игре: `memory.findmatrix` ищет
  матрицы положения математически, по ортонормированности блока 3×3, а
  `arizona.findTexts` перебирает блок памяти и показывает всё, что похоже на
  текст, — так ищется ник в слоте игрока.
